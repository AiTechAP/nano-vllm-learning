# 第 01 章：LLM 推理概述

## 一、大语言模型基础

### 1.1 分词器

分词器 (Tokenizer) 负责把原始文本转换成大模型可识别的一串整数数字 (token_id)，其中每个 token_id 对应词表里的一个子词。后续过程中的计算均以 token_id 为基础，而不是原始的文本字符串。

### 1.2 自回归生成

大语言模型（如 Qwen3、GPT 系列等）是自回归 (autoregressive) 模型，其主要工作原理如下：给定一段文本，大语言模型不会一次性给出全部完整回答，而是先预测下一个 token，然后把预测结果拼接到输入后面，继续预测下一个 token，循环往复，逐个 token 生成，直到输出停止符或达到 token 最大数量时结束。

```
prompt: [t0, t1, t2, t3]

第 1 步: 输入 [t0, t1, t2, t3]      →  模型预测  →  t4
第 2 步: 输入 [t0, t1, t2, t3, t4]  →  模型预测  →  t5
...

直到生成停止符 <EOS> 或达到最大数量 max_num_tokens
```

### 1.3 Decoder-Only Transformer 架构

Decoder-Only Transformer 是一种只使用 Transformer 解码器堆叠而成的生成式模型架构，是目前大语言模型（如 GPT 系列、Qwen3 等）的主流架构，其关键结构模块如下：

```
- 输入层： token 嵌入
- 多层解码器，每层通常包含：
    - 因果掩码多头自注意力：应用自注意力机制，但是每个位置只能看到当前和之前的 token。
    - 前馈神经网络：对每个 token 做非线性变换。
    - 残差连接 + LayerNorm 或 RMSNorm：用于稳定深层网络训练。
- 输出层：先通过线性变换从隐状态维度转换到词表大小，再使用 softmax 计算得到概率分布。
```

## 二、KV Cache

### 2.1 为什么需要 KV Cache

Decoder-Only Transformer 结构在生成第 $n$ 个 token 时，需要计算第 $1$ 个到第 $n$ 个 token 在各层间的 K/V 值，但是第 $1$ 个到第 $n-1$ 个 token 的 K/V 值在前序过程中已经计算过。若每生成一个 token 都要对历史所有 token 重新计算一遍 K/V 值，那么计算量就会随长度平方增长。但是，如果把每一步算出的 K/V 值缓存下来，那么之后每步只需为新 token 算一组 Q/K/V，并与缓存的 K/V 一起计算注意力即可，计算复杂度下降为线性。简单来说，KV Cache 就是把前序 token 已计算的 K 值和 V 值缓存下来。

### 2.2 KV Cache 的显存开销

KV Cache 将计算复杂度从 $O(n²)$ 降到 $O(n)$，但是随之而来的是显存开销的增加。对于一条长度为 $n$ 的序列，其所占显存为：

$$ \text{KV Cache 所需显存} = 2 \times L \times n \times H \times d_h \times b $$

其中，$2$ 是指 K 和 V 各占一份，$L$ 是模型层数，$n$ 是序列总长度，$H$ 是多头注意力的 K/V 头数，$d_h$ 是每个头的维度，$b$ 是每个元素的字节数。

## 三、推理的两个阶段：Prefill 与 Decode

LLM 推理分为性质完全不同的两个阶段：Prefill 阶段和 Decode 阶段。认识和理解 LLM 推理的两个阶段对设计高性能推理引擎非常重要。

- Prefill 阶段：一次性计算所有 prompt token 的 K/V 值。此阶段是计算密集型（compute-bound）。
- Decode 阶段：每步只需要输入上一步新生成的 token，并复用已有 KV Cache，来生成下一个 token。此阶段是访存密集型（memory-bound）。

## 四、批处理

### 4.1 为什么需要批处理

在 Decode 阶段，如果每步只算 1 个 token，那么 GPU 算力的利用率很低。但是，如果把多个请求合并成一个批次一起进行处理，不仅可以提高 GPU 利用率，还能大幅提升吞吐量。

### 4.2 静态批处理

静态批处理把 $N$ 个请求合并成一个批次，等所有请求都运行完成再返回结果，然后再接着处理下一批请求。但是，这种方式需要批次中的所有请求同时开始、同时结束，因此，整批请求的结束时间由最慢的请求决定，而结束早的那些请求空出的 GPU 算力只能不停的空转。此外，新请求至少要等到下一批次才能开始，而不能利用已经空闲的 GPU 算力。

### 4.3 连续批处理

为了解决静态批处理存在的问题，连续批处理 (Continuous Batching) 以轮次为单位进行调度，而不再以批次为单位。具体来说，在任何一步，完成的请求立即离开，只要有空闲算力新请求随时加入，从而使 GPU 持续工作而几乎不空闲，大幅提升 GPU 的利用率。

## 五、PagedAttention

在传统的 KV Cache 显存分配方案中，系统通常为每条请求一次性分配连续显存，并且大小按最大上下文长度预留。但这个方案存在如下几个问题：

1. 内部碎片：新请求进来时，我们不知道它最终的长度，因此，只能为每个请求按最大可能长度预分配 KV Cache。但是实际计算结果如果达不到最大可能长度，预留在后面的一大片显存只能空置，无法给别的请求使用，造成显存碎片。
2. 外部碎片：显存在被不同请求反复分配、释放后，中间产生许多不能利用的小空洞。这将导致即使有足够的总空闲显存，也找不到一块足够大的连续显存来计算新的请求。
3. 无法共享：当多个请求共享相同的前缀时，传统方案必须为每个序列单独存储 KV Cache，造成重复存储而浪费显存。

PagedAttention 的核心思想借鉴了操作系统中虚拟内存的分页技术，它不再要求 KV Cache 必须存储在连续的物理显存中，而是将显存分成大小固定的块 (Block)，并允许这些块可以离散分布在显存中而非连续存储。这些块在计算时按需分配，并且能够在结束后即时释放。对于每个序列，系统通过一个块表 (Block Table) 的映射结构来维护逻辑块与物理块之间的对应关系。

## 六、一次推理请求的链路

一次用户请求，从大模型接收请求一直到返回结果，通常包含如下步骤：

```
接收请求 → 预处理 →  Prefill → Decode → 后处理 → 返回结果
```

- 接收请求：接收 prompt。
- 预处理：对文本做相关的预处理，包括使用分词器把 prompt 字符串转换成 token_id 列表等等。
- Prefill：一次性计算 prompt 所有 token 的 K/V、存储 KV Cache、生成第一个 token。
- Decode：自回归逐个生成 token，同时存储新增的 K/V，直到遇到终止符或者达到最大 token 数停止。
- 后处理：将生成结果解码成文本、并释放 KV Cache 块等后处理操作。
- 返回结果：把生成的文本结果返回给用户。
